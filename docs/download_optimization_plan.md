# Breeze 下载功能优化计划

## 1. 文档目的

本文给出 Breeze 现有漫画下载功能的重构计划。目标不是另起一套与历史数据割裂的新下载器，而是在保留现有离线阅读能力的前提下，逐步解决任务恢复、章节级提交、路径兼容、状态持久化和错误处理等问题。

本计划只讨论下载功能及其直接依赖，不做插件安全审计，也不改变项目“通过插件获取漫画内容”的产品定位。

## 2. 结论摘要

推荐采用以下总体方案：

1. 下载流程从“先获取全部章节图片信息，再一次性下载”改为“逐章节获取、逐章节下载、逐章节提交”。
2. `DownloadTask` 作为可恢复的持久化队列和检查点，记录任务状态、已完成章节和当前进度；正在下载章节的图片清单不跨进程保存。
3. 如果应用在某章节中途退出，下次恢复时重新获取该章节的最新图片清单，但复用磁盘上已经完整写入的图片。
4. 新文件只写入 `encodePath` 生成的标准路径；读取、判重、离线阅读、导出和删除必须统一兼容编码路径与历史原始路径。
5. 不批量搬迁现有图片。历史图片数量和体积较大，采用双路径解析即可兼容，避免升级时长时间占用磁盘和重复复制。
6. 除 `DownloadTask` 外，原则上不修改现有下载业务数据库结构。`UnifiedComicDownload`、旧 Bika/JM 下载记录、书架链接和下载文件均原样保留。
7. 增加一次兼容版本迁移，仅清空旧结构的 `DownloadTask` 数据；迁移之后创建的新任务必须能够跨重启恢复。

## 3. 当前实现与样本基线

### 3.1 当前主要调用链

```text
下载选择页
  -> startDownloadTask
  -> DownloadQueueManager 写入并监听 DownloadTask
  -> unifiedDownloadTask
       -> 获取漫画详情
       -> 获取所有选中章节的图片清单
       -> 合并为一个图片任务列表
       -> 并发下载全部图片
       -> 最后一次性写入 UnifiedComicDownload
  -> 下载书架 / 离线阅读 / 导出
```

主要实现位于：

- `lib/service/download/download_queue_manager.dart`
- `lib/service/download/comic_download_task.dart`
- `lib/service/download/image_download.dart`
- `lib/service/download/models/download_task_json.dart`
- `lib/network/http/picture/picture.dart`

直接关联的外围逻辑包括：

- `lib/page/download/`：章节选择和任务创建。
- `lib/page/donwload_task/`：任务列表、取消和删除。
- `lib/page/comic_read/`：离线图片定位和预读取。
- `lib/page/comic_info/method/export_comic.dart`：下载漫画导出。
- `lib/page/bookshelf/method/import_comic.dart`：漫画导入和编码路径写入。
- `lib/page/bookshelf/service/comic_link_service.dart`：删除下载记录与文件。
- `lib/service/lifecycle/foreground_task/`：Android 前台服务和通知。
- `lib/object_box/model.dart`、`lib/object_box/migration/`：任务实体和兼容迁移。

本计划只读检查了以下 Windows 调试数据：

- ObjectBox 实际目录：`build/windows/x64/runner/db/breeze_db`

3. 数据库中图片的 `path` 仍是逻辑文件名，不是 `encodePath` 结果。这一点应保留：逻辑标识负责数据匹配，编码结果只负责文件系统落盘。

## 4. 现有实现的主要问题

### 4.1 下载启动前必须获取所有章节清单

`unifiedDownloadTask` 先依次获取全部选中章节，再把所有图片放入一个 `jobs` 列表。章节较多时会带来：

- 第一张正文图片开始下载前等待时间较长。
- 任一章节信息获取失败会阻止后续全部下载。
- 图片任务列表和章节响应全部保存在内存中。
- 无法自然地在章节完成时保存检查点。

### 4.2 任务状态可落库，但有效进度仍主要在内存

当前 `DownloadTask` 只保存任务 JSON、两个布尔值和本地化的 `status` 文本。图片完成数、当前章节、已完成章节、失败数等没有稳定的持久化语义。

应用异常退出后只能把 `isDownloading` 重置为 `false` 并重跑整个任务。已有文件可能被跳过，但 UI 无法还原真正进度，也无法区分“已经完整完成的章节”和“中断中的章节”。

### 4.3 下载判重没有完整复用历史路径兼容逻辑

`findCachedPicturePath` 会按“编码路径 -> 原始路径”查找，但 `downloadPicture` 的下载前判重只检查编码后的缓存/下载路径。结果是：

- 离线阅读可能能找到旧文件。
- 同一文件再次下载时却可能无法命中旧文件，从而重复请求和重复落盘。

读取、判重、导出和删除必须使用同一个路径解析器，不能各自拼路径。

### 4.4 只在整个漫画任务末尾提交下载记录

当前只有所有选中章节下载流程结束后才写入 `UnifiedComicDownload`。如果中途退出，即使前面若干章节已经完整落盘，这些章节也没有形成可靠的数据库检查点。

### 4.5 文件直接写入最终路径

`saveImage` 直接写目标文件，文件存在就会被视为可复用。进程在写入中途退出时，可能留下非零但不完整的文件；下一次仅检查 `exists` 或长度时无法判断它是否真正写完。

### 4.6 图片失败被折叠为“继续完成”

图片下载失败和 `404` 经常被转成字符串或在 `_downloadSingleJob` 中吞掉，随后进度仍会增加。这样任务可能显示完成，但元数据中仍引用缺失图片。

### 4.7 取消任务可能影响已经存在的下载

当前取消会按 `source + comicId` 删除整个漫画下载目录。如果用户是在已有下载基础上补充或重新下载章节，取消新任务不应顺带删除原本可离线阅读的历史文件。

### 4.8 标识和状态语义不够稳定

- 去重主要使用 `comicId`，没有把 `source` 纳入任务唯一键。
- 任务状态存储的是本地化展示文本，不适合作为恢复判断依据。
- 漫画 ID、章节匹配 ID、插件请求 ID、存储 ID 和编码后的文件名在多处分别处理，容易出现同一字段在不同模块含义不同的问题。

## 5. 目标行为

### 5.1 正常下载

1. 创建任务并立即持久化选中的章节引用。
2. 获取一次最新漫画详情，用于刷新漫画元数据并匹配选中章节。
3. 按确定顺序逐章处理。
4. 每章开始时获取该章节当前的图片清单。
5. 对该章图片并发下载；命中编码路径或旧原始路径都算已存在。
6. 图片成功完整落盘后，再更新进度。
7. 整章达到完成条件后，合并写入 `UnifiedComicDownload`，同时保存任务检查点。
8. 所有选中章节完成后标记任务完成，并清理已完成任务行。

### 5.2 中断与恢复

如果应用在某一章节下载中途退出：

- 已经提交完成的章节不再重新获取和下载。
- 当前未完成章节的图片清单不作为恢复依据，下次必须重新调用插件获取。
- 新清单中的图片逐个通过统一路径解析器判重，磁盘上已有的完整文件直接复用。
- 当前章节的图片数量、顺序或 URL 发生变化时，以恢复时的新清单为准。
- 旧清单中已经不再出现的文件暂不自动删除，避免恢复过程做大范围文件清理；后续可单独增加“清理孤立文件”功能。

这正好满足“章节图片不一定固定”的约束：保存章节级结果，不保存未完成章节的易变图片清单。

### 5.3 已有漫画补充章节

- 读取现有 `UnifiedComicDownload` 的章节列表。
- 使用既有 `DownloadChapterAdapter` 语义匹配章节：优先逻辑 key，同时兼容请求 ID、旧 ID 和 order 回退。
- 新完成章节与旧章节做合并或替换，不再用本次选中章节整体覆盖旧记录。
- 保留原 `createdAt`，更新 `updatedAt`；`downloadedAt` 的含义应统一为最近一次成功提交章节的时间。
- 书架根链接使用幂等写入，已有链接不重复创建。

### 5.4 取消、失败和重试

- 取消只停止当前任务并清理该任务的 `.part` 临时文件。
- 已经提交完成的章节和任务开始前就存在的旧下载不得删除。
- 可重试错误保留任务和检查点，状态置为 `failed` 或 `retryWaiting`。
- 明确资源不存在与重试耗尽必须产生结构化结果，不能只依靠字符串 `404`。
- 默认情况下，只要仍有未成功处理的正文图片，章节就不能标记为完整完成；UI 可显示失败图片数并提供重试。

## 6. 目标架构

### 6.1 组件划分

建议把 `lib/service/download/` 调整为以下职责。文件名可在实施时微调，但边界应保持：

```text
download/
  download_queue_manager.dart       队列串行调度、启动恢复、取消入口
  download_task_repository.dart     DownloadTask 的读取和原子状态更新
  comic_download_executor.dart      漫画级编排、详情刷新、最终完成
  chapter_download_executor.dart    单章清单获取、图片下载、章节提交
  download_asset_store.dart         路径候选、判重、原子写入、删除
  download_progress.dart            结构化进度模型和聚合
  download_progress_reporter.dart   UI/通知适配，不参与状态判断
  download_cancel_signal.dart       取消信号
  models/
    download_task_payload.dart      用户选择的稳定输入
    download_checkpoint.dart        可恢复检查点
    download_result.dart            图片/章节的结构化结果
```

核心约束：

- 队列管理器不直接实现漫画和图片业务。
- UI 和通知只消费结构化状态，不把展示字符串写回业务状态。
- 网络获取与文件存储解耦，路径兼容集中到 `DownloadAssetStore`。
- Android 前台服务、macOS activity 和 iOS 生命周期只负责平台保活或展示，不拥有下载队列。

### 6.2 队列并发策略

第一阶段保持现有用户体验和资源占用水平：

- 漫画任务并发：1。
- 当前章节内图片并发：默认 5。
- 并发数由执行器显式持有，不在多个 helper 中各自创建不相关的池。
- 取消时停止领取新图片任务，并等待或取消正在进行的插件请求。

先完成状态正确性和兼容性，再根据真实测量决定是否做动态并发、自适应限速或多漫画并行。

## 7. 持久化设计

### 7.1 `DownloadTask` 的定位

`DownloadTask` 只作为“待执行队列 + 恢复日志”，不作为长期下载历史。完成的漫画历史仍由 `UnifiedComicDownload` 表示。

建议的新任务字段如下：

| 字段 | 用途 |
| --- | --- |
| `id` | ObjectBox ID |
| `taskKey` | `$source:$comicId`，任务唯一键 |
| `schemaVersion` | 任务 JSON/检查点版本 |
| `source` | 插件 ID |
| `comicId` | 漫画逻辑 ID |
| `comicName` | 任务列表展示名 |
| `stateCode` | `queued/running/failed/completed/cancelled` |
| `phaseCode` | 当前细分阶段 |
| `payloadJson` | 选中的章节引用及稳定任务输入 |
| `checkpointJson` | 已完成章节 key、当前章节、持久化进度计数 |
| `attempt` | 任务执行尝试次数 |
| `lastErrorCode` / `lastErrorMessage` | 最近一次失败信息 |
| `createdAt` / `updatedAt` | 排序、恢复和诊断 |

如果希望尽量减少 ObjectBox 列，也可以把 payload 和 checkpoint 放入一个带 `schemaVersion` 的 JSON 字段；但 `taskKey`、`stateCode`、`createdAt` 和 `updatedAt` 最好保留为可查询字段。

### 7.2 检查点内容

需要持久化：

- 选中的章节稳定引用。
- 已完成章节的 canonical key。
- 当前章节 key。
- 当前阶段。
- 已完成章节数/总章节数。
- 当前章节已完成、已复用、失败和总图片数。
- 最近错误和尝试次数。

不应跨进程持久化：

- 未完成章节的完整图片 URL/路径清单。
- 插件运行时对象。
- 正在执行的 Future、Pool 或取消对象。

进度写库采用节流方式，例如每秒最多一次或每完成若干图片一次；章节完成、状态切换和错误发生时必须立即落库。

### 7.3 状态机

建议的任务阶段：

```text
queued
  -> preparingRuntime
  -> fetchingComicInfo
  -> fetchingChapterInfo
  -> downloadingChapter
  -> committingChapter
  -> fetchingChapterInfo ...
  -> completed

任意运行阶段 -> retryWaiting / failed / cancelled
应用重启时任意运行阶段 -> queued（保留章节检查点）
```

数据库只保存状态 code；中文、英文等展示文本由 UI 和通知层根据 code 与进度参数生成。

## 8. 章节级执行与提交

### 8.1 单章处理顺序

```text
读取任务检查点
  -> 跳过已完成章节
  -> 获取当前章节最新清单
  -> 建立本次内存图片任务
  -> 统一解析新旧文件候选
  -> 下载缺失图片到临时文件
  -> 原子替换为最终文件
  -> 校验本章完成条件
  -> 合并章节元数据到 UnifiedComicDownload
  -> 保存章节完成检查点
```

### 8.2 提交顺序

必须保证以下恢复性质：

1. 图片文件先完整落盘，再提交引用它的章节元数据。
2. 如果图片已落盘但数据库提交前退出，下次重新获取该章清单后会命中文件，不需要再次下载。
3. 如果章节数据库已提交但任务检查点更新前退出，恢复时可同时检查 `UnifiedComicDownload` 和磁盘，幂等地把该章标记完成。
4. 同一章节重复提交必须是 upsert，而不是追加重复章节。

ObjectBox 若无法把任务检查点和漫画记录放在同一个简单事务中，也要通过幂等合并保证上述顺序可重复执行。

### 8.3 章节合并键

章节合并沿用现有兼容语义：

1. `logicalKey` / canonical `DownloadChapter.id`。
2. `requestId` / `taskChapterId`。
3. 历史 `id`。
4. 最后使用 `order` 作为兼容回退。

新写入数据继续显式保存 `logicalKey`、`taskChapterId` 和 `storageChapterId`，但不能重写旧记录中原有 key 的含义。

## 9. 文件路径与历史数据兼容

### 9.1 标准写入布局

新下载继续使用当前编码方案：

```text
downloads/
  <pluginId>/
    original/
      <encodePath(comicId)>/
        <encodePath(storageChapterId)>/
          <encodePath(normalizedImagePath)>
```

封面位于漫画目录下，不包含章节目录。`encodePath` 当前由 Rust 使用 `xxh3_128` 计算并生成 `f_<数字>`，应保持算法稳定，不能在本次重构中更换 hash 算法。

### 9.2 统一候选解析

`DownloadAssetStore` 对同一逻辑图片生成有序候选：

1. 当前平台下的标准编码下载路径。
2. 当前平台下的历史原始下载路径。
3. 标准编码缓存路径。
4. 历史原始缓存路径。
5. 对确实存在的导入绝对路径做兼容直查。

具体缓存和下载优先级可以按现有阅读行为保留，但所有调用方必须复用同一个候选生成函数。

| 操作 | 编码路径 | 历史原始路径 |
| --- | --- | --- |
| 新写入 | 是 | 否 |
| 下载前判重 | 是 | 是 |
| 离线阅读 | 是 | 是 |
| 图片尺寸预读 | 是 | 是 |
| 漫画导出 | 是 | 是 |
| 删除整部漫画 | 删除 | 删除 |

### 9.3 不做批量文件迁移

本次升级不把 6.39 GB 历史图片统一重命名或复制到编码目录，理由如下：

- 升级时间不可控。
- 复制可能瞬间占用接近双倍磁盘。
- 中断后的迁移恢复会引入另一套复杂状态。
- 双路径读取已经能够满足兼容目标。

如果未来确实希望统一目录，可另做显式的“整理下载存储”功能，并提供进度、暂停、空间检查和失败恢复；它不应阻塞本次下载重构。

### 9.4 `storageRoot` 处理

- 读取时不信任 `UnifiedComicDownload.storageRoot` 的绝对值。
- 实际根目录始终由当前平台的 `getDownloadPath()` 与逻辑标识计算。
- 新写入可继续填充该字段以便调试，但不能让阅读、导出或删除依赖它。
- 不批量改写现有 104 条记录的 `storageRoot`。

## 10. 文件写入完整性

新下载文件采用临时文件加原子重命名：

```text
<finalName>.part.<taskId> -> 写入并 flush -> 基本校验 -> rename 到 <finalName>
```

要求：

- 最终路径在完整写入前不能出现。
- 取消只清理属于当前 task ID 的临时文件。
- 启动恢复时可以清理已不存在任务对应的过期 `.part` 文件。
- 已有历史文件不要求重新校验或改写；只有实际读取失败时才按既有策略重新下载。
- “文件存在”与“本次下载成功”使用结构化结果区分，例如 `existingLegacy`、`existingCanonical`、`downloaded`、`failed`。

## 11. 数据迁移计划

建议新增兼容迁移 `v9 -> v10`：

1. 调整 `DownloadTask` 实体和任务 JSON 模型。
2. 运行 ObjectBox/Freezed/JSON 代码生成，保留既有实体和字段 UID 的稳定性。
3. 在 `migration_v9_to_v10.dart` 中仅执行 `downloadTaskBox.removeAll()`。
4. 把 `compatible.dart` 的最新版本更新为 `v10`。
5. 不修改或删除以下数据：
   - `UnifiedComicDownload`
   - `BikaComicDownload`
   - `JmDownload`
   - `ComicLink` / 下载文件夹数据
   - `files/downloads` 下的任何历史图片
6. 迁移完成后再启动新队列监听，避免旧 JSON 被新调度器解析。

清空旧 `DownloadTask` 是一次性迁移行为。迁移完成后，新任务不能再在普通启动时被清空；运行中状态应恢复为 `queued` 并从章节检查点继续。

## 12. 分阶段实施计划

### 阶段 0：建立兼容基线和测试夹具

- 从现有样本提取去隐私化的小型 fixture，不把用户实际漫画标题和完整数据库提交进仓库。
- fixture 至少包含：纯原始路径、纯编码路径、二者共存、comic ID 含 `/`、旧章节字段缺失和跨平台 `storageRoot`。
- 记录改造前能够离线打开、导出和删除的样本集合，作为回归基线。

完成标准：兼容场景可以在不启动真实插件的情况下重复测试。

### 阶段 1：统一路径解析与原子文件存储

- 新增 `DownloadAssetStore`/路径值对象。
- 把 `findCachedPicturePath`、`downloadPicture` 判重、导出和删除逐步切换到统一候选。
- 新写入使用 `.part.<taskId>` 和原子重命名。
- 保留旧公开函数作为薄适配层，减少一次性调用方改动。

完成标准：旧原始文件可被下载判重命中，不会因重跑任务产生第二份编码文件。

### 阶段 2：任务模型、迁移和状态机

- 重构 `DownloadTask` 和版本化 payload/checkpoint。
- 增加 `v9 -> v10` 清理迁移。
- 建立 `DownloadTaskRepository`，所有任务状态修改从一个入口完成。
- 任务唯一键改为 `source + comicId`。
- 启动恢复不再只修改布尔值，而是执行明确的状态转换。

完成标准：任务在排队、获取详情、获取章节和下载图片阶段退出后，重启都能重新进入队列，UI 能显示持久化进度。

### 阶段 3：逐章节执行与检查点

- 把 `unifiedDownloadTask` 拆分为漫画级和章节级执行器。
- 删除“先构造全部章节 `chapterResponses` 和全部图片 `jobs`”的主流程。
- 当前章节清单只保存在内存；恢复时重新获取。
- 每个章节完成后立即提交元数据和检查点。

完成标准：前一章节完成后强制结束应用，重启只重新获取未完成章节，已完成章节可离线阅读。

### 阶段 4：下载记录合并、错误语义和 UI

- 将 `_saveUnifiedDownload` 改为幂等 upsert/章节合并。
- 引入结构化图片结果，移除业务判断对字符串 `404` 和本地化 `status` 的依赖。
- 任务页显示漫画进度、章节进度、复用数、失败数和可重试状态。
- 通知层继续消费相同结构化进度。

完成标准：补充章节不会覆盖旧章节；图片失败不会被静默计入成功。

### 阶段 5：取消、生命周期和全平台验证

- 取消仅清理当前任务临时文件，不删除既有已提交下载。
- Android 验证前台服务启动、强制结束后的恢复和通知更新。
- iOS 只验证前台下载及应用重新打开后的恢复，不把系统级后台持续运行作为目标。
- Windows、Linux、macOS 验证相同核心逻辑和平台路径。

完成标准：五个平台共用相同任务状态机，平台差异只停留在生命周期和通知适配层。

### 阶段 6：清理旧实现

- 删除已无调用的内存进度和重复路径拼接代码。
- 保留历史原始路径读取分支，不设未经验证的删除期限。
- 更新下载相关注释和开发文档。

完成标准：全局搜索不存在绕过统一资产存储层直接拼接漫画下载路径的新代码。

## 13. 测试计划

### 13.1 单元测试

路径与文件：

- 编码文件存在时优先命中。
- 只有原始文件存在时仍能判重、阅读和导出。
- 编码和原始文件同时存在时结果稳定。
- comic ID、章节 ID 或图片路径含 `/`、`\`、空格和特殊字符时，新写入仍只有安全的编码段。
- `.part` 文件不被当作完整图片。
- 写入失败或取消后不留下最终文件。

状态机：

- 每个运行阶段重启都转换为可恢复状态。
- 已完成章节检查点不会倒退。
- 同一任务重复调度不会产生两个执行器。
- 相同 `comicId`、不同 `source` 可以分别排队。
- 失败任务保留检查点并可重试。

章节数据：

- 未完成章节恢复时重新获取清单。
- 新清单增加、删除、调整图片顺序或更换 URL 时，以新清单为准。
- 旧章节字段组合仍可被 `DownloadChapterAdapter` 匹配。
- 章节重复提交不会产生重复记录。

迁移：

- `v9 -> v10` 只清空旧任务。
- 统一下载、旧 Bika/JM 数据、书架链接的数量和内容不变。
- 下载目录没有文件被迁移代码改名或删除。

### 13.2 集成测试

使用可控的假插件或本地 fixture 模拟：

1. 两章漫画，第一章完成后中断，第二次启动继续第二章。
2. 单章下载一半后中断，第二次获取到变化后的图片清单。
3. 旧原始路径已存在，新任务直接复用。
4. 某张图片前两次失败、第三次成功。
5. 永久失败后任务停留在可重试状态，不显示完整完成。
6. 已下载漫画补充章节时取消，新章节停止但旧章节仍可阅读。

### 13.3 样本数据回归

对当前 Windows 样本的副本验证：

- 迁移前后 104 条统一下载记录均保留。
- 迁移前能够离线打开的页面，迁移后仍能打开。
- 旧原始图片不会因为判重失败而被重复下载到编码路径。
- 导出和删除同时覆盖原始布局与编码布局。
- 数据库中来自 Android 的绝对 `storageRoot` 不影响 Windows 读取。

## 14. 验收标准

满足以下条件后，下载重构才算完成：

1. 应用重启后无需重新创建任务，队列能恢复。
2. 中断章节会重新获取章节清单；已完成章节不会重复获取。
3. 当前章节已有的完整图片可复用，包括旧原始路径图片。
4. 每完成一章就形成可恢复的数据库检查点。
5. 新文件只写编码路径，历史文件无需批量迁移。
6. 旧统一下载、旧 Bika/JM 记录、书架链接和历史文件不因升级丢失。
7. 补充或重下章节使用合并语义，不覆盖其他已下载章节。
8. 取消新任务不会删除任务开始前已经存在的下载。
9. 临时或不完整文件不会被误判为下载成功。
10. 图片失败可见、可重试，不被静默计入完成。
11. 业务状态不依赖本地化字符串。
12. Android、Windows、Linux、macOS、iOS 使用同一核心调度与恢复逻辑；iOS 不承诺系统限制之外的后台持续下载。

## 15. 建议的首个开发切片

首个可独立合并的切片应只做“路径统一与兼容判重”，暂不改任务表和调度流程：

1. 为一张图片生成编码与原始路径候选。
2. 让 `downloadPicture` 和 `findCachedPicturePath` 共用候选解析。
3. 为原始文件命中、编码文件命中和二者共存补测试。
4. 让导出与删除复用同一资产存储层。

这一切片可以立即消除旧图片被重复下载的问题，也是后续章节恢复能够正确复用历史文件的基础。完成后再进入 `DownloadTask` v10 和章节级流水线，改动风险更容易控制。
